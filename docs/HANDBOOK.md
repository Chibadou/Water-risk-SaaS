## 2. Architecture — concepts clés

- **Toutes les APIs externes passent par des routes serveur** (`app/api/*`) : pas de CORS, gestion d'erreur centralisée, cache `next: { revalidate }`. Les erreurs upstream retournent des messages français exploitables par l'UI (jamais de crash).
- **Sources** : VigiEau (`/api/zones`, 404 = non couvert, 409 = commune multi-zones — on envoie toujours lon/lat), BAN `data.geopf.fr/geocodage` (**l'ancien api-adresse.data.gouv.fr est mort**), Hub'Eau hydrométrie/piézométrie (~20 req/s fair-use, rayon 60 km, sondage parallèle de 8 candidates max), CSV arrêtés data.gouv (historique), Explore2 TRACC (projections).
- **Score composite** (`lib/score.ts`) : réglementaire 40 % + fréquence structurelle 25 % + Onde 10 % + tendance débit 12,5 % + tendance nappe 12,5 %, **renormalisé sur les composantes disponibles**. Une composante inconnue = `undefined` (jamais 0 par défaut — cf. « VigiEau down ⇒ historique inconnu, pas 0 j »). La composante fréquence utilise la **moyenne structurelle multi-années** (`joursAlertePlusMoyen`) quand des années complètes existent, sinon le cumul de l'année en cours. Reste à venir (`UPCOMING_COMPONENTS`) : IPS nappes, débits vs VCN10/QMNA5, BNPE.
- **Classification du risque** (Sprint 12, `lib/score.ts`) : le score 0-100 est traduit en 6 classes nommées (Négligeable / Faible / Modéré / Élevé / Très élevé / Critique), alignées sur la terminologie WRI/CDP. Un **indicateur de confiance** (haute/moyenne/faible) agrège couverture des composantes, distance de la station rattachée et fraîcheur des données.
- **Calendrier saisonnier** (Sprint 12) : répartition mensuelle des jours en alerte+ sur les années complètes. Source : `parMois` dans `ZoneHistory` (agrégation mensuelle ajoutée à `lib/history.ts`). Visualisé dans `RestrictionHistory.tsx` via `computeSeasonalProfile` (`lib/score.ts`).
- **Évolution du risque** (Sprint 12) : courbe de la composante « fréquence » année par année (sparkline SVG). Détecte les tendances d'aggravation/amélioration.
- **Seuils de projection** (Sprint 12) : le bloc 2050 croise le Δ VCN10 projeté avec la fréquence structurelle pour qualifier la tension future (bloc `ThresholdInsight` dans `Projection2050.tsx`).
- **Secteur d'activité = contrôle unique** (Sprint 13, fusionné avec le profil au post-Sprint 17, `lib/secteur.ts`) : 6 secteurs (agriculture/industrie/énergie/services/collectivité/autre) avec impact opérationnel détaillé par niveau de gravité (`SectorImpactPanel.tsx`). ⚠️ **Il n'y a plus qu'un seul menu déroulant** (dans `AddressSearch.tsx`) : le secteur remplace l'ancien sélecteur de « profil ». Le **profil VigiEau est dérivé** du secteur via `profilForSecteur` (agriculture→exploitation, collectivité→collectivité, industrie/énergie/services/autre→entreprise). Le secteur pilote donc à la fois la requête VigiEau (restrictions applicables) ET l'interprétation d'impact — **sans double comptage** (le secteur n'entre jamais dans `computeScore`). `SavedSite` garde `profil` (dérivé, pour la requête + rétro-compat) + `secteur`. Rétro-compat : liens/sites hérités sans secteur → `secteurForProfil` infère. **« Particulier » (usage domestique) est conservé mais marqué secondaire** (`domestic: true` dans `SECTEURS`) : présenté dans un `<optgroup>` distinct de `AddressSearch`, avec un encart dans `SectorImpactPanel` précisant que l'outil vise les sites professionnels. Il fonctionne comme les autres (profil VigiEau `particulier` + table d'impacts domestiques). Test : `npx tsx scripts/test/secteur.test.ts`.
- **Synthèse portefeuille** (Sprint 13) : le dashboard affiche des indicateurs agrégés (nombre de sites, score moyen, score max, répartition par classe de risque). Chaque site porte un badge de classe de risque WRI/CDP à côté du score. L'export CSV inclut le secteur et la classe de risque.
- **Lien de partage** (Sprint 14) : bouton « 🔗 Partager » qui copie une URL encodant l'analyse complète (lat/lon/label/profil/**secteur**). `buildParams`/`parseInitialParams` dans `HomeClient.tsx` gèrent l'aller-retour ; le secteur est restauré à l'ouverture d'un lien. Zéro serveur — tout tient dans l'URL, cohérent avec le local-only.
- **Mode hors-ligne (PWA)** (Sprint 14) : `public/manifest.webmanifest` + service worker `public/sw.js` enregistré en prod uniquement (`ServiceWorkerRegister.tsx`, monté dans `app/layout.tsx`). Stratégie : network-first pour les navigations, stale-while-revalidate pour les assets Next, **`/api/*` jamais mis en cache** (données live, egress requis, pas de risque périmé servi comme actuel). Le shell + le dashboard localStorage marchent hors-ligne ; les données temps réel restent « indisponibles ». ⚠️ Le SW ne s'enregistre pas en dev (conflit Turbopack). Pour tester : `npm run build && npx next start`, puis DevTools → Application → Service Workers.
- **Benchmark projection** (Sprint 15) : le bloc 2050 situe la baisse d'étiage projetée du site (médiane VCN10 à +2,7 °C) dans la distribution nationale (34 418 communes) + départementale. Distribution de référence pré-calculée **hors-ligne** depuis les shards Explore2 déjà embarqués par `scripts/projections/build_benchmark.py` → `data/projections/benchmark.json` (58 Ko, 101 breakpoints de percentile par scope). Loader `benchmarkForCommune` (`lib/projections.ts`), helper pur `severityPercentile` (`lib/projectionsShared.ts`, testé), remonté dans `ProjectionPayload.benchmark`, affiché par `BenchmarkInsight` (`Projection2050.tsx`). ⚠️ Si les shards Explore2 changent, **régénérer** le benchmark (le script relit les shards locaux, aucun egress). Test : `npx tsx scripts/test/benchmark.test.ts`.
- **Répartition géographique du portefeuille** (Sprint 16) : le dashboard regroupe les sites par département (`PortfolioByDepartment.tsx`) avec nombre de sites + score moyen, classés du risque le plus élevé au plus faible (effet « heatmap » par barre colorée). Département déduit du `citycode` via `departementCode` (`lib/departements.ts`, référentiel statique embarqué : 96 métro + Corse 2A/2B + DOM 971-976), testé (`scripts/test/departements.test.ts`). Ne s'affiche que si les sites couvrent ≥2 départements. ⚠️ Pas de vraie choroplèthe départementale (géométries non embarquées, egress bloqué) — c'est une agrégation, pas une carte polygonale ; noté en backlog.
- **Rapport ESG / ESRS E3** (Sprint 17, `lib/report.ts`) : builder pur `buildMarkdownReport(input)` → Markdown structuré (identification, score + décomposition, statut réglementaire, historique, projection 2050 + benchmark, correspondance ESRS E3/TNFD/CDP, sources + avertissement). Assemble les données déjà à l'écran ; le bouton « 📄 Rapport ESG » (`HomeClient.tsx`) fetch la projection à la volée puis télécharge un `.md`. 100 % navigateur, aucune donnée serveur. `reportFilename` slugifie le libellé. Testé (`scripts/test/report.test.ts`). C'est un **support de contexte**, pas une déclaration de conformité (avertissement explicite dans le rapport).
- **Carte choroplèthe départementale** (Sprint 19-B) : sur le dashboard, `PortfolioChoropleth.tsx` (MapLibre, fond neutre sans tuiles externes) teinte chaque département selon le score moyen des sites qu'il contient. Polygones départementaux simplifiés récupérés **via GitHub Actions** (egress bloqué en dev — voir workflow `fetch-refdata.yml` + script `scripts/refdata/fetch_refdata.py`), coords arrondies à ~100 m, servis par `/api/departements` (`data/refdata/departements.geojson`, 226 Ko, 96 départements). Inclus dans `outputFileTracingIncludes`.
- **Indice d'anticipation** (Sprint 20, `lib/anticipation.ts` + `AnticipationPanel.tsx`) : comble l'**horizon temporel manquant** entre le statut VigiEau *maintenant* et la projection *2050* — les prochaines semaines jusqu'à la fin de l'étiage, dont une entreprise a besoin pour **anticiper** un passage/aggravation en restriction. Fonction pure `computeAnticipation(input)` : deux volets. (1) **Base saisonnière = l'ancre** — pic du risque mensuel historique (`computeSeasonalProfile`, réutilisé, désormais avec un `currentYear` injectable pour les tests) sur les mois de l'horizon (mois courant + 2) ; hors saison, gate l'indice bas quel que soit l'état physique (les arrêtés sécheresse sont saisonniers). (2) **Pression état actuel** — signaux précurseurs déjà calculés, normalisés 0-100 : IPS nappe (poids le plus fort — signal le plus lent/prédictif), débit VCN10/QMNA5, assecs Onde, niveau VigiEau courant, chaque signal physique nuancé par sa tendance 14 j ; ce volet ne relève l'indice que si la saison est « ouverte » (`openness = seasonalBase/40`). Combinaison `seasonalBase*0.5 + stateScore*0.5*openness`, puis **facteur de trajectoire** (cumul jours alerte+ de l'année en cours vs moyenne au même stade → ×0.85-1.20) et **plancher** si déjà en restriction (alerte→55, crise→75). Sortie = 4 niveaux (Peu probable/Possible/Probable/Très probable) + **moteurs détaillés** + confiance (réutilise la logique de `scoreConfidence`) + avertissement « conditions propices, pas une prévision de l'arrêté ». **100 % in-repo, aucun egress** : `AnticipationPanel` calcule à partir des props déjà en state dans `HomeClient` (histInfo/onde/indicators) — dégradation gracieuse tant que les signaux Hub'Eau ne sont pas arrivés. Placé entre l'historique et le bloc 2050. Test : `npx tsx scripts/test/anticipation.test.ts`.
- **Prévision de nappe MétéEAU : lien sortant, PAS d'intégration** (post-Sprint 20, `lib/meteeau.ts`) — ⚠️ **tranché, ne pas re-prober.** Le follow-up « prévision nappe » a été instruit en 5 passes Actions. Constat : l'API **MétéEAU des nappes** (`api.meteeaunappes.brgm.fr`) existe et conviendrait parfaitement (prévision IPS 6 mois par `code_bss`, seuils saisonniers) mais elle est **verrouillée par OAuth2** — Keycloak BRGM, `security` global sur *toutes* les opérations, 401 `WWW-Authenticate: Bearer` — et **aucun dataset de prévision n'est publié sur data.gouv**. Ré-héberger serait en outre non viable (couverture nationale, péremption mensuelle) et juridiquement incertain. **Décision utilisateur : renvoyer par un lien.** `AnticipationPanel` affiche donc, **dans les deux états** (indice disponible ou non), un lien vers le visualiseur public + un encart expliquant *pourquoi* c'est un lien (`METEEAU_WHY_LINK`) — exigence explicite : l'utilisateur doit le comprendre sans aller dans la méthodologie. ⚠️ **L'URL publique n'est pas `meteeaunappes.brgm.fr`** (site Drupal institutionnel) mais **`https://app.meteeaunappes.brgm.fr/`** (SPA Angular, le vrai visualiseur) — trouvé en crawlant les liens *hors-domaine* du Drupal. Pas de schéma de centrage lat/lon confirmé (routes Angular dans les bundles JS, non inspectées) → `METEEAU_SUPPORTS_CENTERING = false`, on n'invente pas de paramètres que le visualiseur ignorerait ; passer le flag à `true` suffirait si une route de centrage était confirmée un jour. **La prévision n'entre pas dans le score** : la dimension nappe de l'indice reste l'IPS *observé* (Hub'Eau/ADES ouvert). Le scaffolding de probe (`scripts/nappe/`, workflow, `data/refdata/nappe-*.json`) a été **purgé** après analyse (convention « diag à purger ») — récupérable dans l'historique git (commits `67ff056`→`0c82bdb`).
- **Jours d'activité contrainte** (Sprint 21, `lib/interruption.ts` + `lib/restrictions.ts` + `InterruptionPanel.tsx`) : la **synthèse** qui fait enfin parler entre eux les arrêtés, l'anticipation et la projection. `jours contraints = Σ jours(niveau) × exposition(niveau)` — pondération **bornée**, jamais un quotient (la forme `probabilité × durée / priorité` initialement envisagée donnait 180 j d'interruption dans une sécheresse de 90 j). Trois horizons : *année type* (moyenne des **années complètes uniquement** — `parAnnee` contient aussi l'année en cours partielle, cf. `lib/history.ts:313-319`), *fin de saison* (climatologie mensuelle × ajustement dérivé de `AnticipationResult.index`, **consommé** et non redupliqué), *2050* (`dtBE_yr` allonge en jours, `VCN10_ete` intensifie en décalant les jours vers le niveau supérieur **en cascade descendante, total conservé**). Test : `npx tsx scripts/test/interruption.test.ts`.
- **⚠️ L'exposition est LUE dans les arrêtés, jamais posée** (`lib/restrictions.ts`) — c'est le cœur du Sprint 21 et une correction explicite de l'utilisateur (« ne pas inventer de coefficients »). La ressource « Restrictions » **n'a pas de champ de sévérité structuré** : `usage.u.description` est de la prose préfectorale. Mais elle est régulière et souvent **chiffrée** : « Interdiction de 8h à 20h » = 12 h/24 = 0,5, mesuré ; les pourcentages sont parsés. À défaut de quantité : interdiction 1,0 · interdiction avec dérogation (« sauf ») 0,85 · sensibilisation 0. **Illisible ⇒ `undefined`, jamais 0.** Exposition = **moyenne** sur les usages dont le drapeau `concerne_<profil>` est vrai — *pas* un max : un usage interdit sur quinze n'arrête pas un site. Tests calibrés sur des libellés **verbatim** du fichier (`scripts/test/restrictions.test.ts`). ⚠️ Ordre des tests important : `AWARENESS` avant `NO_LIMIT` (des mesures disent les deux), et les formes chiffrées avant les formes grossières.
- **Origine de l'eau** (Sprint 21, `levelForOrigin` dans `lib/vigieau.ts`) : VigiEau publie un niveau **par type de zone** (SUP/SOU/AEP) et `worstLevel` prend le **max** — prudent pour le score, faux pour l'impact opérationnel (un site sur réseau AEP héritait de la gravité d'une nappe qu'il ne pompe pas). `levelForOrigin` vit **à côté** ; `worstLevel` est **inchangé** pour ne pas déplacer le score des sites déjà enregistrés. Défaut `inconnu` = comportement historique.
- **Données restrictions embarquées** (`data/restrictions/`, construites par `scripts/restrictions/build_restrictions.py` via Actions) : `guide.json` = **matrice nationale officielle** « Restriction Guide Sécheresse » (20 usages × 4 niveaux × 4 audiences, 19 Ko) servant de **repli** ; `zones/<dep>.json` = usages restreints publiés par département (99 shards, 7,6 Mo, plus gros 273 Ko). Servis par `/api/restrictions?dep=&type=&profil=` → exposition par niveau + détail auditable. **Aucun egress à l'exécution** (la source fait 23 Mo). ⚠️ **Le classifieur de sévérité n'est PAS réimplémenté en Python** : le script ne fait que réduire la source aux tuples distincts, le classifieur TS unique les score — sinon les deux dérivent en silence. `outputFileTracingIncludes` mis à jour.
- **BNPE : le milieu EST récupérable** (Sprint 21, `lib/bnpe.ts`) — ⚠️ **corrige une note erronée de ce HANDBOOK.** « La chronique BNPE n'a pas de champ milieu » est vrai *de la chronique*, mais `referentiel/ouvrages` porte `code_type_milieu` / `libelle_type_milieu` (+ `code_bdlisa`) et se joint sur `code_ouvrage`. Probe mesuré : **taux de jointure 1,0** (Chartres : eau potable = superficiel, industrie = souterrain). `aggregateBnpe(rows, milieuByOuvrage?)` produit désormais `parUsage[].parMilieu` et `parMilieu`. Un ouvrage non joint reste en `inconnu` (jamais écarté) ; si **aucun** ne se joint, `milieuAvailable: false` plutôt qu'un seau unique présenté comme une répartition.
- **Arbitrage des usages** (Sprint 21, `lib/arbitrage.ts` + `BnpePanel`) : hiérarchie du **décret n° 2021-795** (usages d'agrément restreints en premier → eau potable/santé/sécurité maintenues en dernier), secteur du site mis en évidence. **Purement descriptif** — aucun chiffre du produit n'en dérive. Répond à la question « une entreprise en crise ne peut-elle plus prélever ? » : non, seuls les prélèvements *non prioritaires* cessent.
- **ZRE hors métropole : instruit, aucune source — ⚠️ ne pas re-prober.** Le WFS Sandre annonce `sa:ZRE` **à côté** de `sa:ZRE_FXX`. `sa:ZRE` se lit correctement (en `OUTPUTFORMAT=geojson` ; `application/json` renvoie 400), mais il produit **exactement le même contenu** : reconstruction identique à **13 033 communes sur 64 départements**, Corse et outre-mer vides. Aucune couche ZRE plus large n'est exposée par ce service. On ne peut pas distinguer d'ici « ces territoires n'ont pas de ZRE » de « la couche les omet » — d'où le maintien de `available: false` pour 2A/2B/97x/98x dans `/api/transition`, qui est la lecture prudente et correcte.
- **Explore2 : QMNA5 et recharge de nappe n'existent PAS dans cette collection — ⚠️ ne pas re-chercher.** L'énumération complète des ressources des deux jeux TRACC (agrégé et détaillé) ne contient que **quatre indicateurs** : `VCN10_été`, `QA_yr`, `dtBE_yr`, et `QJXA_yr`/`dtCrues_yr`. Les trois premiers sont déjà extraits ; les deux derniers sont des indicateurs de **crue**, hors sujet pour un produit de pénurie. La recharge des nappes relèverait du volet souterrain DRIAS-Eau / Aqui-FR, **un autre jeu de données** — la projection des zones SOU continue donc de s'appuyer sur un indicateur de débit de surface, limite à assumer telle quelle.
- **Humidité des sols (SWI)** (Sprint 23, `lib/swi.ts` + `/api/swi` + `scripts/swi/build_swi.py`) : précurseur le plus **précoce** de la chaîne (le sol s'assèche des semaines avant la nappe), standardisé comme l'IPS — rang de la valeur du mois dans la distribution de la **même maille SAFRAN** pour le **même mois calendaire** sur 1990-2019. ⚠️ **Séparation embarqué / live délibérée**, sur le précédent MétéEAU : la climatologie (8 981 mailles × 12 mois → `data/swi/clim/*.json`, 3,9 Mo en 40 buckets, + `cells.json` 340 Ko) est stable et embarquée ; le **mois courant n'est jamais embarqué** (il se périmerait en silence) et se récupère à la volée depuis le fichier décennal `swi.202001-202512.csv` (~22 Mo, cache 24 h), même schéma que le CSV des arrêtés. Poids dans `computeAnticipation` : **12**, sous la nappe (30) — signal plus rapide donc plus bruité. Tests : `npx tsx scripts/test/swi.test.ts`.
- **⚠️ SWI : le CRS documenté est FAUX.** Le jeu data.gouv annonce « Lambert 2 étendu, en hectomètres » ; les valeurs réelles (`LAMBX≈641374`, `LAMBY≈7106309`) ne collent qu'au **Lambert-93 en mètres (EPSG:2154)**. Le script de build ne fait donc confiance à aucune des deux : il essaie les candidats et retient celui dont les mailles converties tombent dans l'emprise France — mesuré **100 % pour Lambert-93 m, 0 % pour les trois autres** — et sort en erreur si aucun ne passe. Ne pas « corriger » vers la doc.
- **Colonnes réelles du SWI** : `NUMERO, LAMBX, LAMBY, DATE (AAAAMM), SWI_UNIF_MENS`. ⚠️ La ressource au format `csv` du jeu est une **notice**, pas des données — les données sont les fichiers `swi.<AAAAMM>-<AAAAMM>.csv` au format **`csv.gz`**. Une première passe s'y est trompée et a rapporté une ligne de commentaire comme schéma.

- **Export PDF du rapport ESG** (post-Sprint 20, `lib/reportHtml.ts`) : choix retenu = **impression navigateur**, pas de librairie de rendu (cohérent avec le refus des deps lourdes déjà pris pour Playwright — pas d'entrée package.json — et avec le principe local-only, aucun aller-retour serveur). `markdownToHtml(markdown)` convertit le sous-ensemble Markdown **contrôlé** produit par `buildMarkdownReport`/`buildPortfolioMarkdownReport` (titres, tableaux, listes, gras/italique) en HTML sémantique — pas un parseur Markdown générique, seulement ce que les builders émettent réellement. Tout le texte est **échappé** avant insertion (les libellés de site viennent de la BAN, donc du texte utilisateur). `reportPrintHtml(markdown, title)` enveloppe le résultat dans un document HTML autonome avec CSS `@media print` (masque la barre d'action à l'impression, évite les coupures de tableau/liste) et un bouton « 🖨️ Imprimer / Enregistrer en PDF » (`window.print()`). Boutons « 🖨️ Version PDF » (fiche site, `HomeClient.tsx`) et « 🖨️ PDF » (portefeuille, `SitesDashboard.tsx`) à côté du bouton Markdown existant, même flux de données (aucune duplication de la logique d'assemblage). ⚠️ **`window.open()` doit rester dans le préfixe synchrone du handler** (avant tout `await`) sinon les bloqueurs de popup l'interceptent — c'est pourquoi la fenêtre est ouverte avec un HTML de chargement *avant* le fetch de la projection, puis son contenu est réécrit une fois le rapport prêt (`HomeClient.tsx`, `exportReport`). **Repli si popup bloquée** : téléchargement du HTML imprimable en `.html` (le fichier s'ouvre et s'imprime localement). Testé (`scripts/test/report.test.ts` : rendu des titres/tableaux/listes/gras, échappement HTML sur un libellé malveillant, document complet).
- **Projections 2050** (`lib/projections.ts` + `data/projections/`) : données réelles Explore2 TRACC **par commune (bassin versant)**, lookup par code INSEE (arrondissements 751xx/132xx/6938x normalisés vers 75056/13055/69123), repli lat/lon → commune via geo.api.gouv.fr. 96 shards JSON par département, embarqués via `outputFileTracingIncludes` dans `next.config.ts`. `meta.json` porte la provenance et le flag `demo` (bandeau UI automatique).
